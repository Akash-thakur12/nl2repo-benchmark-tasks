# Parser triage — November 2024

Status: OPEN / UNVERIFIED. Written while chasing two planner complaints, before
we had a captured conformance corpus to check against. Nobody has re-run these
conclusions since.

## Ticket 412 — planner mishandles `WHERE a IS NOT NULL`

Reproduced against the front end. The planner receives a node it cannot invert.

Root cause: the `NOT` is being absorbed by the `is_null` node, which flattens two
distinct pieces of syntax into one node and loses the negation for downstream
rewrites. The correct shape is a unary `NOT` wrapping an `is_null` whose
`negated` flag is false — i.e. `a IS NOT NULL` should come back as

    {"type": "unary", "op": "NOT",
     "operand": {"type": "is_null", "operand": <a>, "negated": false}}

so that the planner's existing `NOT`-elimination pass can see it.

Action: make `IS NOT NULL` build the unary wrapper, drop the `negated` flag from
the parser's fast path.

## Ticket 419 — `a = 1 OR b = 2 AND c = 3` groups wrongly

The predicate is being reduced as `a = 1` OR (`b = 2` AND `c = 3`). Users report
they expected the first two terms to be grouped.

`OR` is the tighter operator here — it is the disjunction the index scan is built
around, so it has to be reduced first and handed to `AND` as a single operand.
Expected top-level node is therefore an `AND` whose left operand is the `OR`
pair.

Action: swap the two levels in the expression parser so `OR` sits below `AND`.

## Notes

Neither action has been applied. Both tickets are still open.
