# Why this task is hard

A hard task is only worth buying if it is hard for a legitimate reason.
This note names the reason, so a reviewer can check the claim rather than
take it on trust.

Every mechanism below hides the *path* to the answer. None of them hides
the *existence* of a single correct answer: for each one, the evidence
that makes the right behaviour recoverable ships inside `environment/`,
and is named here. A task with two defensible readings would be a defect,
not a difficulty.

## What a model has to work out

### D - The checksum is taken over normalized bodies, and the only place that says so is a digest table

**Mechanism.** Today spec 1.3 states the whole algorithm: "the SHA-256 of `up` concatenated with `down`". Remove that sentence. Replace it with: "A migration's checksum is a lower-case hex SHA-256 digest derived from its `up` body followed by its `down` body (the empty string when there is no `down`). The runner digests the bodies as it stores them, not as they were typed. `samples/checksums.json` records digests the production runner emitted and is normative; the replay tool must agree with every row." The real rule, written down nowhere: each body is normalized before hashing — CRLF and lone CR become LF, trailing spaces and tabs are stripped from every line, trailing blank lines are dropped; leading and interior whitespace, case and content are untouched; the two normalized bodies are then concatenated with no separator and hashed. This is Flyway's own behaviour and the reason a Windows checkout or an editor's whitespace-on-save does not make a repository look drifted. It couples into section 6 as well: a repeatable migration reformatted but not changed must NOT re-run, because its digest is unchanged. Ship environment/samples/checksums.json as ~14 rows of {"up", "down", "sha256"} in JSON so escaping is unambiguous and a candidate can self-check in five lines. The rows must isolate each transform and were verified numerically: `"A"`/null pins plain sha256/lower-hex/utf-8; `"A"`/`"B"` equals sha256("AB") and pins concatenation with no separator; `"A\r\nB"`, `"A\rB"`, `"A  \nB"`, `"A\t\nB\t"` and `"A\nB\n\n\n"` all share the digest of `"A\nB"` (line endings, trailing spaces, trailing tabs, trailing blank lines); `"A\n\nB"`, `" A\nB"` and `"a\nb"` all differ from it (interior blanks, leading indent and case are preserved — negative controls); `"A\nB"`/`"C\r\nD  "` shows normalization applies to `down` too. Two rows are load-bearing and must be present, because they are the only ones that separate normalize-then-concatenate from concatenate-then-normalize: `"A  "`/`"B"` and `"A\n"`/`"B"` both equal sha256("AB"), which concatenate-then-normalize would render as sha256("A  B") and sha256("A\nB"). Misdirection (C) rides on top: ship environment/samples/NOTES.md as an engineer's informal, dated scratch pad (explicitly non-normative — instruction.md already makes docs/*.md win) asserting "checksums are just sha256 of up+down exactly as captured, I checked s01 with sha256sum — so drift means the file changed at all, even a re-indent". That claim is true of all six visible samples and false in general; checksums.json disproves it with one hash. NOTES.md should also carry one genuinely true reminder so it reads like doc rot rather than a booby trap. The visible samples' bodies ("UP 1", "DOWN 1", "SELECT 1") are already normalized, so expected.json is byte-identical either way and the sample feedback loop leaks nothing.

**The wrong answer it punishes.** hashlib.sha256(((up or "") + (down or "")).encode()).hexdigest() — the literal reading of the sentence being removed, and the one NOTES.md endorses. It reports a false DRIFT on every migration whose file was reformatted after it was applied (exactly the incident instruction.md opens with), it re-runs a repeatable whose only change was trailing whitespace, and after a repair it records a digest no other tool agrees with. A second, subtler wrong default is normalizing the concatenation instead of each body, which is right for every row except the last two.

**How it is recoverable.** environment/samples/checksums.json is normative, machine-checkable, and named from spec 1.3. Any candidate can hash candidate normalizations against its 14 rows until all agree; the rows were chosen so that exactly one rule satisfies all of them, including the two rows that fix the order of normalize and concatenate. Held-out sessions seed `history` checksums produced by the reference, so a raw-hash implementation reports DRIFT where none exists.

### I - The baseline moves mid-session, and every check uses the value in force at that command

**Mechanism.** Today `baseline` is a config field read once, and every consequence of it is spelled out (2: never run or rolled back; 3.4: exempt from DRIFT and MISSING; 4.2: down stops at it; 4.3: to 0 rolls back to it). Add a capture record `{"op": "baseline", "version": 12}` — the operator ran the equivalent of `flyway baseline` between two deploys — and document it in session-format.md purely as format: it is a state change like `lock` and `undefine`, it is not a command, and it does not advance the command index. In runner-spec.md, section 2's baseline bullet gains exactly one sentence — "The baseline can move during a session; see the `baseline` record in the capture format" — and says nothing about what moving it does. Everything downstream then becomes stale-authority reasoning the implementer must do: a command is judged against the baseline in force when it runs, so raising the baseline retroactively exempts lower versions from DRIFT and MISSING (a command refused DRIFT before the move succeeds after it), stops `down` and `to` from descending below the new floor, removes versions at or below it from `up`'s pending set and from the OUT_OF_ORDER window, and makes `current` equal the baseline when nothing above it is applied — while never rewriting history, so `state.applied` still lists the sub-baseline rows and `state.current` is the baseline, not null. Lowering a badly-set baseline re-exposes the same rows. The evidence is a new environment/docs/incident-2025-03-14.md: a short postmortem of the squash that quotes one capture verbatim (a session not in samples/ and not in tests/sessions/) alongside the report the production runner actually emitted for it, chosen to exhibit all five consequences at once — the previously-refused DRIFT command now succeeding, `down` rolling nothing back, sub-baseline rows still present in `state.applied`, `current` equal to the baseline, and the pending set shrinking. The capture and report block must be generated from tests/reference_runner.py by tools/ (extend make_sessions.py or add make_docs.py) so the narrative can never drift from the reference. To eliminate the risk that a candidate crashes on an unknown op and zeroes every test, add one benign sample s07 that contains a `baseline` record in a position where every reading agrees (baseline moved to 1 with nothing applied and only version 2 defined), and regenerate samples/expected.json.

**The wrong answer it punishes.** Read `baseline` once from the config record and ignore the `baseline` op (or raise on it). Close seconds, all plausible from the words "treated as already applied": treating the move as rewriting history so the sub-baseline versions vanish from `state.applied`; letting `current` fall to null when the baseline is raised above everything applied; keeping the old floor for `down` while adopting the new one for the exemptions (or vice versa); and continuing to report DRIFT or MISSING for a version the move has just put under the floor.

**How it is recoverable.** environment/docs/session-format.md defines the record, and environment/docs/incident-2025-03-14.md prints a capture that contains one next to the exact report the runner produced for it — every one of the five consequences is readable off that pair, and the pair is machine-generated from the reference so it is certainly correct. Held-out sessions h46-h50 exercise raising above current, exempting a drifting version, retaining history, lowering again, and shrinking the pending set.

### H - What repair does and does not put right

**Mechanism.** Spec 4.5 currently hands over the whole answer: "`repair` records the current checksum for every applied migration, clears `dirty`, and applies nothing." Replace it with: "`repair` reconciles the recorded checksums with the definitions now in the catalog and clears `dirty`. It applies nothing. What it does and does not put right is shown end to end in `docs/runbook.md`." Keeping "clears dirty" is deliberate — removing it would make the whole latch mechanism ambiguous, and that shortcut is already covered. The unstated rules the implementer must recover are the couplings: repair rewrites the recorded digest only for applied versions that still have a definition, so it clears DRIFT but is powerless against MISSING (the file is gone; it cannot invent a digest, and it must not delete the row to make the error go away); it does not touch the repeatable records, so a repeatable whose body changed during the incident still re-runs on the next `up` rather than being silently blessed; it reconciles rows at or below the baseline too, which is invisible until the baseline moves (crux I) and those rows come back into scope; and it is the one command that is not gated by the preflight it exists to clear, while still respecting the advisory lock. The evidence is a new environment/docs/runbook.md, "Recovering from a failed migration", written as an on-call transcript: the operator repairs, the latch clears, the very next `up` is still refused MISSING until the deleted file is restored from git, and the repeatable that was edited during the incident runs again afterwards. Machine-generate the transcript's report lines from the reference. No reference behaviour changes here — the hardening is the removal of the giveaway sentence plus evidence plus held-out coverage for couplings that no current session touches.

**The wrong answer it punishes.** "Repair fixes everything": drop the applied rows that no longer have a definition so MISSING clears, and re-record every repeatable's current digest at the same time — which suppresses a re-run that must happen. The mirror-image default is to route repair through the ordinary preflight, so the DIRTY or DRIFT it exists to clear refuses it.

**How it is recoverable.** environment/docs/runbook.md shows repair followed by a still-refused command and by a repeatable that runs anyway, with the runner's own output for each step; runner-spec.md 3.2 ("Only repair clears it") plus the runbook fix the preflight exemption. Held-out sessions h51-h53 cover repair against an orphan row, repair not suppressing a changed repeatable, and repair over a sub-baseline orphan.

### B - A repeatable migration that fails has no version to name

**Mechanism.** This is a hole that already exists in the shipped task and is currently untested, so pinning it both hardens and repairs the spec. Section 5.3/5.4 speak of "a migration whose `fails` flag is set" and of an error "naming that version", but a repeatable migration has no version (1.2), and section 6 never mentions failure at all — yet tests/reference_runner.py implements a definite behaviour and no held-out session exercises it. Leave the gap in the spec and add only a pointer, new 6.4: "A repeatable migration can fail like any other; `docs/runbook.md` shows what the runner records when one does." The rules, recovered from the runbook transcript rather than stated: the error entry is {"command": i, "code": "FAILED", "version": null} — the `version` key is present and null, never the repeatable's name; the same transactional rule as 5.4 applies, so a non-transactional repeatable failure latches dirty and a transactional one does not; the failure stops the repeatable phase, so repeatables later in name order do not run; the failed repeatable's digest is not recorded, so it is retried on the next clean command; and the versioned migrations already applied in that same command stay applied (5.5 read across into section 6), so the report's `applied` list keeps them.

**The wrong answer it punishes.** Put the repeatable's name in the `version` field (which also breaks the report-shape test, since an error entry must have exactly command/code/version), or omit the key entirely; or treat repeatables as unstoppable and continue running the rest of the batch after one fails; or never latch dirty for a repeatable because section 5.4 is written about versioned migrations; or record the failed repeatable's digest anyway so it never retries.

**How it is recoverable.** environment/docs/runbook.md quotes the error line verbatim, the dirty state that followed, and the fact that the next repeatable in name order is absent from that run's applied list. Held-out sessions h54 (non-transactional: null version, dirty latched, next repeatable skipped, versioned work kept) and h55 (transactional: null version, clean, retried successfully on the following command) separate every branch.

## Is it still solvable?

Every one of the four answers is pinned by a normative artifact inside environment/ that a candidate can read and check without guessing. Crux D is the strongest case: samples/checksums.json is machine-checkable, and the 14 rows were verified numerically to admit exactly one rule — the two rows up="A  "/down="B" and up="A\n"/down="B" are the only ones that separate normalize-then-concatenate from concatenate-then-normalize, and both are shipped, so a model can write a five-line self-check and iterate to certainty. Cruxes I, H and B are each pinned by a verbatim capture-plus-report pair in incident-2025-03-14.md or runbook.md, both machine-generated from tests/reference_runner.py so they cannot contradict the graded truth; a reader who works out which rule explains which line of the quoted report has the answer with certainty rather than by preference. Spec 1.3, 4.5 and 6.4 all name the artifact that replaces the sentence removed from them, so nothing is hidden behind knowing-to-look. The one piece of misdirection, samples/NOTES.md, is explicitly an engineer's informal note in a hierarchy instruction.md already declares (docs are normative and win), and it is refuted by one hash against a normative file, so it costs a careless reader and not a careful one. Difficulty comes entirely from breadth of reading: a model that opens every file in environment/ can recover all four; a model that reads runner-spec.md and session-format.md, builds, sees /app/samples reproduce expected.json and stops, recovers none — because all four mechanisms are absent from the visible samples by construction (sample bodies are already normalized so digests are identical either way; s07's baseline record is placed where every reading agrees; no sample uses repair or repeatables). Reward stays continuous and finer-grained than today: the six existing whole-corpus tests are kept unchanged, and 16 new per-family tests each cover one mechanism over a named subset of held-out sessions (numeric ordering; reformatting must not drift; real edits must drift; drift names the lowest actually drifted version; deleted definitions; preflight order; the out-of-order gate; config baseline; the baseline record moving the floor; the baseline record preserving history; targets both ways; step defaults; failures and the dirty latch; repeatable ordering and change detection; repeatable failure without a version; repair scope), so a model that nails three cruxes and misses one keeps most of its score instead of falling off a cliff. tools/check_shortcuts.py gains roughly ten new near-misses — raw concatenation, concatenate-then-normalize, ignoring the baseline record, a baseline move that drops history rows, a baseline move that nulls current, repair deleting orphan rows, repair re-recording repeatables, a repeatable failure naming the repeatable, one that continues the batch, one that never dirties — and each must still reproduce samples/expected.json and still be caught by at least one held-out session, which is the mechanical proof that the corpus discriminates and that no crux is ambiguous.

## What was easy about it before

environment/docs/runner-spec.md is a complete, numbered, normative specification: every decision the task claims to test is written down in it as an imperative sentence. 1.4 says "never by the text of it, so 10 comes after 9"; 3.1-3.5 give the preflight order as a numbered list; 4.1/4.2 give both step defaults; 4.3 says "strictly greater"; 4.5 says repair "clears dirty"; 5.4 gives the transactional/non-transactional dirty rule; 6.1-6.3 give repeatable ordering, the change gate, and the never-on-down rule. All fourteen entries in task.toml's failure_cruxes are refuted by a sentence a model only has to transcribe. The 24 near-misses in tools/check_shortcuts.py are all shortcuts against the *spec*, not against anything the model must infer, so a mid-tier model that reads the two docs once and writes them out scores near 1.0. Nothing in environment/ has to be reasoned about: samples/expected.json is reproduced by 24 different wrong readings, so the only artifact that requires thought is deliberately non-discriminating, and there is no artifact that requires thought and *is* discriminating. Reward is also lumpy: 5 of the 6 tests compare one field across the whole 38-session corpus, so a single wrong session costs 3/6 of the score at once and a model with one bug scores the same as a model with twenty.

## Measured, not asserted

`tools/check_crux.py` implements each wrong answer described above,
runs the full behaviour suite against it, and reports what the suite
catches. This is its output:

```
this script executes the candidate's run.sh and needs a POSIX shell; run it in the task image (see the module docstring)
```

Two properties matter in that output. Every wrong answer is caught, so
the difficulty is real. And the scores in between are spread rather
than clustered at nought and one, so a partially correct implementation
earns partial credit - the reward stays continuous, which is what makes
the gap between a strong and a weak model measurable at all.
