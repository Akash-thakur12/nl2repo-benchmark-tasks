# INC-4602 - prerequisite cycles were being reported as prerequisite failures

Status: resolved in v3.0. Referenced by flag-spec.md §5.1.

## What happened

An operator added a prerequisite that closed a loop between two flags. The
service detected the loop correctly, but the evaluation that the caller saw came
back as `PREREQUISITE_FAILED`, which sent the on-call engineer looking at the
prerequisite's targeting rules for forty minutes. Worse, in one configuration
the loop was invisible: the cycling flag's `off_variant` happened to equal the
variant the dependant required, so the prerequisite "passed" and the dependant
served a targeted value out of a broken configuration.

From v3.0 a cycle is treated as a configuration fault for the whole evaluation,
not as one prerequisite that failed. The evaluation is abandoned as soon as the
loop is seen and the **entry** flag - the flag the caller asked about - reports
its own `off_variant` with reason `CYCLE`. Nothing between the entry flag and
the loop gets a say.

## Decision records

Exported verbatim from the audit log. `request.flag` is the flag the caller
asked for; `decision` is what the caller received.

### (a) two-flag loop, entered at `a`

```json
{"definitions": [
   {"key": "a", "enabled": true, "off_variant": "shut", "default_variant": "on",
    "prerequisites": [{"flag": "b", "variant": "on"}]},
   {"key": "b", "enabled": true, "off_variant": "off", "default_variant": "on",
    "prerequisites": [{"flag": "a", "variant": "on"}]}],
 "request": {"flag": "a", "user": "u1"},
 "decision": {"flag": "a", "variant": "shut", "reason": "CYCLE"}}
```

The reported variant is `shut` - flag `a`'s `off_variant`, not flag `b`'s. The
entry flag reports; the flag where the loop was detected does not.

### (b) three-flag chain `a -> b -> c -> b`, entered at `a`

```json
{"definitions": [
   {"key": "a", "enabled": true, "off_variant": "a-off", "default_variant": "on",
    "prerequisites": [{"flag": "b", "variant": "on"}]},
   {"key": "b", "enabled": true, "off_variant": "b-off", "default_variant": "on",
    "prerequisites": [{"flag": "c", "variant": "on"}]},
   {"key": "c", "enabled": true, "off_variant": "c-off", "default_variant": "on",
    "prerequisites": [{"flag": "b", "variant": "on"}]}],
 "request": {"flag": "a", "user": "u1"},
 "decision": {"flag": "a", "variant": "a-off", "reason": "CYCLE"}}
```

`a` is not itself part of the loop - the loop is `b -> c -> b` - and `a` still
reports `CYCLE` with its own `off_variant`. Depth does not matter.

### (c) the case that made this a Sev-2: `off_variant` equal to the required variant

```json
{"definitions": [
   {"key": "a", "enabled": true, "off_variant": "shut", "default_variant": "on",
    "prerequisites": [{"flag": "b", "variant": "on"}]},
   {"key": "b", "enabled": true, "off_variant": "on", "default_variant": "on",
    "prerequisites": [{"flag": "a", "variant": "on"}]}],
 "request": {"flag": "a", "user": "u1"},
 "decision": {"flag": "a", "variant": "shut", "reason": "CYCLE"}}
```

Under v2 this returned `{"variant": "on", "reason": "DEFAULT"}`: `b`'s cycle
result `on` was compared against the required `on`, the prerequisite was
declared satisfied, and `a` fell through to its default. Both the variant and
the reason are different under v3. This record is the discriminator - an
implementation that only renames the reason string still gets this one wrong.

### (d) for completeness: the same loop entered at `b`

```json
{"definitions": "as in (c)",
 "request": {"flag": "b", "user": "u1"},
 "decision": {"flag": "b", "variant": "on", "reason": "CYCLE"}}
```

`on` here is `b`'s own `off_variant`, because `b` is now the entry flag.
